## 2. 首次初始化

使用本机 Node.js 24（24.11+）、pnpm 10.34.9 与可用的 Docker Engine/Compose。可继续通过 nvm 管理 Node；`.node-version` 记录默认版本，不要求切换到精确补丁版本。

在仓库根目录依次执行：

```bash
pnpm install --frozen-lockfile
pnpm local:init
pnpm local:doctor
pnpm db:up
pnpm db:bootstrap
pnpm db:migrate
pnpm db:check
pnpm dev
```

- 打开 <http://127.0.0.1:3000>；页面与 API 共用进程和端口。
- PG 映射到 `127.0.0.1:55432`，数据保存在 Compose 的 `tandem_postgres-data` 卷中。
- `local:init` 生成随机数据库密码及 `.env`，重复执行保留已有配置，只补充缺失的会话加密密钥；`.env.example` 不含可用密码。改端口或库名时同步更新连接 URL 和 `TANDEM_PUBLIC_URL`。
- `db:bootstrap` 由管理账号安装扩展、建立角色和 schema，不修改已有角色密码；`db:migrate` 使用独立迁移账号。Web/Worker 启动不执行 DDL。
- `dev` 启动前端与独立 Worker；Ctrl+C 停止本次进程。前端支持热更新，修改 Worker 后重启开发命令。
- 分开启动使用 `dev:web`、`dev:worker`。本地启动器筛选环境变量：Web 不接收模型 Key，Worker 使用独立数据库账号，两个进程均不接收管理库连接。
- 真实 T 组执行需配置模型服务、固定执行镜像和共享产物目录；MCP 需部署端 allowlist。完整环境变量及配置边界见 [07](07-一期实现与验收.md#2-运行配置)。

缺少 pnpm 时执行 `npm install --global pnpm@10.34.9`，之后直接使用 `pnpm`。项目命令是 `local:init`、`local:doctor`；`pnpm setup` 和 `pnpm doctor` 是包管理器自己的命令。

## 3. 构建与启动

```bash
pnpm build
pnpm start
# 另一个终端
pnpm start:worker
```

构建会生成 Next.js standalone、Worker 和 MCP 入口，并复制主服务静态资源及 `public/`。Windows 上重新构建前先停止运行中的 standalone 服务，避免目录被占用。宿主启动脚本将 `TANDEM_ARTIFACT_ROOT` 解析为仓库下的绝对路径，默认 `data/delivery/`；Web/Worker 必须访问同一目录。

MCP 客户端配置以 `node apps/mcp/dist/index.js` 为命令，工作目录设为仓库根目录；stdio 的 stdout 只用于协议，日志写 stderr。通过客户端私密环境注入 `TANDEM_MCP_BASE_URL`、`TANDEM_MCP_ACCOUNT`、`TANDEM_MCP_PASSWORD`，以本人协作账号调用主服务；任务写入只创建草案，批准须在产品中完成。工具清单见 [07](07-一期实现与验收.md#5-产品-api-与对外-mcp)。

容器方式使用同一数据库，先完成第 2 节的 bootstrap/migrate，再执行：

```bash
docker compose -f compose.yaml -f compose.app.yaml up -d --build --wait
pnpm test:containers
```

主服务和 Worker 使用不同启动目标，独立重启；非 root、只读根文件系统、临时目录、资源限额与健康检查已配置。Worker 通过自身 ID 对应的 PG 心跳检查，无 HTTP 端口。Worker 镜像目前复用构建阶段，包含构建依赖；后续发布时可进一步裁剪镜像。

这是**工程基础容器验收配置**，只监听 loopback。现有 Compose 尚未为 Worker 注入完整业务身份/模型配置，也未配置共享产物卷和隔离执行入口；不能据此验收 T 组交付。完整业务当前按上述宿主双进程方式运行。正式部署还须配置 TLS/入口网关、密钥管理及备份策略，本配置不代表产品已可公网使用。

切回本机开发前停止容器中的 Web/Worker，避免抢占端口：

```bash
docker compose -f compose.yaml -f compose.app.yaml stop web worker
pnpm dev
```

停止数据库用 `pnpm db:down`；不删除数据卷。不要把 `docker compose down -v` 当常规停止操作。

## 4. 数据与运行规则

- `0001` 建立基础队列；`0002` 增加身份、会话、空间成员、团队和 Agent；`0003`–`0008` 增加项目引用/授权、草案、交付、能力及执行检查点等自有资产。不复制外部项目、任务与工时。
- 业务迁移放在 `packages/storage-postgres/migrations/`。迁移按文件名排序、加数据库锁、逐文件事务执行并保存 SHA-256；已执行文件不可改写，后续修改新增迁移。
- `withScope` 在事务中设置空间及用户上下文；提交/回滚后连接无残留。空间资源 RLS 同时检查实际成员关系；项目访问需显式授权及当前上游权限，空间成员资格不等于项目授权。
- 调度账号只对队列表具有跨空间领取权限，不具备表 owner、超级用户或 BYPASSRLS 权限；业务资源访问仍需使用可信作用域并校验当前授权。
- 队列按空间和去重键唯一；同键内容不一致拒绝。使用 `SKIP LOCKED`、租约与递增执行令牌，续租、完成、失败及检查点写入都核对当前令牌与有效租约。
- 只有可安全重放的工作才可使用租约恢复；外部副作用经草案服务核对版本、身份、执行回执和幂等。结果未知先核对，不直接套用队列重试。
- Worker 注册 `system.diagnostic`、`draft.execute` 和 `delivery.run`，业务处理器在 `apps/worker/src/product-handlers.ts` 组装。未知任务明确失败，不返回虚假成功。
- 文件产物默认保存于 `data/delivery/`，技能资源包与运行产物经路径校验，预览和 ZIP 下载经空间/项目授权；生成代码、测试和构建在基本隔离环境执行。运行模式、产物证据及本地演示发布边界见 [07](07-一期实现与验收.md)。

健康接口不包含凭证、数据库地址或内部异常：

| 接口                    | 语义                                                    |
| ----------------------- | ------------------------------------------------------- |
| `GET /api/health/live`  | 主服务存活；200 不表示数据库或 Worker 正常              |
| `GET /api/health/ready` | 数据库连接、schema 版本及 pgvector 就绪则 200，否则 503 |
| Worker 心跳             | 独立检查后台可用性，不因 Worker 离线关闭主服务页面      |

## 5. 开发验证

```bash
pnpm format:check
pnpm check
pnpm test:integration
pnpm build
pnpm test:collaboration
# 启动主服务后
pnpm smoke
pnpm exec playwright install chromium
pnpm test:e2e
# 容器方式启动后
pnpm test:containers
```

集成测试创建随机命名的独立测试数据库，结束时仅清理该测试库；不向本地开发库填业务数据。浏览器测试通过接口替身验证异常、权限撤销及范围切换；`test:collaboration` 使用隔离数据库和仅存在于测试中的协作服务，验证真实生产构建的 HTTP 链路。项目/能力/交付专项测试，以及会写入专用本机验收对象的 `test:product` 见 [07](07-一期实现与验收.md#6-验证与证据)。真实站点兼容性需另外联调。

CI 配置在 `.github/workflows/ci.yml`，覆盖格式、静态检查、PG 集成、构建、MCP/HTTP 冒烟和浏览器用例。远端执行结果以 GitHub 实际运行记录为准。

## 6. 备份与恢复

```bash
pnpm db:backup
pnpm db:restore:check
```

备份保存在被 Git 忽略的 `data/backups/`。恢复检查选择最新备份，创建独立临时库，验证扩展、schema、应用权限及 RLS 后清理，**不会覆盖原库**。生产恢复须同时保留数据库角色/密钥和产物存储；当前脚本演练的是同一 PG 实例内的基础数据库恢复，不宣称已验证跨机器灾备或业务产物一致性。
