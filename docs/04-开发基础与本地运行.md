# 开发基础与本地运行

## 1. 本阶段边界

工程基础已落地，账号、空间成员与 T 组初始化在此基础上接入。三份设计文档仍是产品与架构基线；业务能力进度与登录配置见 [05 协作基础与认证](05-协作基础与认证.md)。

| 模块    | 当前实现                                                                               |
| ------- | -------------------------------------------------------------------------------------- |
| 工作区  | pnpm workspace、锁文件、Node 版本、严格 TypeScript、ESLint、Prettier、依赖边界检查     |
| Web/API | Next.js 单端口、antd/Tailwind、CSS token、协作工作台、错误/404、健康检查               |
| Worker  | 无 HTTP 端口；PG 领取、心跳、续租、执行令牌、检查点、关闭宽限与过期接管                |
| PG      | PostgreSQL 17 + pgvector 0.8.2；独立迁移/应用/Worker 账号、事务、RLS、版本及校验和迁移 |
| MCP     | stdio 协议入口，可握手并返回空工具列表；没有业务读写工具                               |
| 适配层  | 协作账号认证连接器；模型、外部 MCP、执行器保留端口，尚未接入                           |
| 验证    | 单元、真实 PG 集成、浏览器、冒烟、容器生命周期及备份恢复脚本                           |
| 交付    | Docker 多阶段构建、Compose、CI 工作流、本地运行说明                                    |

项目授权与读取、草案审批、Agent Loop、Skills/MCP 管理和隔离执行器属于后续功能开发。当前没有派活或任意命令执行入口，不使用模拟结果冒充执行成功。

## 2. 首次初始化

要求 Node.js 22.13+（固定版本见 `.node-version`）、Corepack 与可用的 Docker Engine/Compose。

在仓库根目录依次执行：

```bash
corepack pnpm install --frozen-lockfile
corepack pnpm local:init
corepack pnpm local:doctor
corepack pnpm db:up
corepack pnpm db:bootstrap
corepack pnpm db:migrate
corepack pnpm db:check
corepack pnpm dev
```

- 打开 <http://127.0.0.1:3000>；页面与 API 共用进程和端口。
- PG 映射到 `127.0.0.1:55432`，数据保存在 Compose 的 `tandem_postgres-data` 卷中。
- `local:init` 生成随机数据库密码及 `.env`，重复执行保留已有配置，只补充缺失的会话加密密钥；`.env.example` 不含可用密码。改端口或库名时同步更新连接 URL 和 `TANDEM_PUBLIC_URL`。
- `db:bootstrap` 由管理账号安装扩展、建立角色和 schema，不修改已有角色密码；`db:migrate` 使用独立迁移账号。Web/Worker 启动不执行 DDL。
- `dev` 启动前端与独立 Worker；Ctrl+C 停止本次进程。前端支持热更新，修改 Worker 后重启开发命令。
- 分开启动使用 `dev:web`、`dev:worker`。本地启动器筛选环境变量，管理库连接及其他进程凭证不会传入应用子进程。

Windows 全局 pnpm 失效时，使用 `corepack pnpm` 或 `.\scripts\pnpm.cmd`。项目命令是 `local:init`、`local:doctor`；`pnpm setup` 和 `pnpm doctor` 是包管理器自己的命令。

## 3. 构建与启动

```bash
corepack pnpm build
corepack pnpm start
# 另一个终端
corepack pnpm start:worker
```

构建会生成 Next.js standalone、Worker 和 MCP 入口，并复制主服务静态资源。Windows 上重新构建前先停止运行中的 standalone 服务，避免目录被占用。

MCP 客户端配置以 `node apps/mcp/dist/index.js` 为命令，工作目录设为仓库根目录；stdio 的 stdout 只用于协议，日志写 stderr。接入认证与共享应用用例之前不注册业务工具。

容器方式使用同一数据库，先完成第 2 节的 bootstrap/migrate，再执行：

```bash
docker compose -f compose.yaml -f compose.app.yaml up -d --build --wait
corepack pnpm test:containers
```

主服务和 Worker 使用不同启动目标，独立重启；非 root、只读根文件系统、临时目录、资源限额与健康检查已配置。Worker 通过自身 ID 对应的 PG 心跳检查，无 HTTP 端口。Worker 镜像目前复用构建阶段，包含构建依赖；后续发布时可进一步裁剪镜像。

这是**本地开发/容器验收配置**，只监听 loopback。正式部署须配置身份连接、TLS/入口网关、密钥管理及备份策略；本配置不代表产品已可公网使用。

切回本机开发前停止容器中的 Web/Worker，避免抢占端口：

```bash
docker compose -f compose.yaml -f compose.app.yaml stop web worker
corepack pnpm dev
```

停止数据库用 `corepack pnpm db:down`；不删除数据卷。不要把 `docker compose down -v` 当常规停止操作。

## 4. 数据与运行规则

- `0001` 建立基础队列；`0002` 增加身份、会话、空间成员、团队和 Agent。不复制外部项目、任务与工时。
- 业务迁移放在 `packages/storage-postgres/migrations/`。迁移按文件名排序、加数据库锁、逐文件事务执行并保存 SHA-256；已执行文件不可改写，后续修改新增迁移。
- `withScope` 在事务中设置空间及用户上下文；提交/回滚后连接无残留。`0002` 的空间资源 RLS 同时检查实际成员关系；外部项目仍默认拒绝，空间成员资格不等于项目授权。
- 调度账号只对队列表具有跨空间领取权限，不具备表 owner、超级用户或 BYPASSRLS 权限；业务资源访问仍需使用可信作用域并校验当前授权。
- 队列按空间和去重键唯一；同键内容不一致拒绝。使用 `SKIP LOCKED`、租约与递增执行令牌，续租、完成、失败及检查点写入都核对当前令牌与有效租约。
- 只有可安全重放的工作才可使用租约恢复；外部副作用必须在后续草案服务中核对回执和幂等，不可直接套用队列重试。
- 当前唯一处理器为内部 `system.diagnostic`。未知任务明确失败；没有“未实现却返回成功”的业务处理器。
- 文件产物预留 `data/artifacts/`。尚未开放文件上传、下载与执行；后续启用前实现路径、权限与隔离检查。

健康接口不包含凭证、数据库地址或内部异常：

| 接口                    | 语义                                                    |
| ----------------------- | ------------------------------------------------------- |
| `GET /api/health/live`  | 主服务存活；200 不表示数据库或 Worker 正常              |
| `GET /api/health/ready` | 数据库连接、schema 版本及 pgvector 就绪则 200，否则 503 |
| Worker 心跳             | 独立检查后台可用性，不因 Worker 离线关闭主服务页面      |

## 5. 开发验证

```bash
corepack pnpm format:check
corepack pnpm check
corepack pnpm test:integration
corepack pnpm build
corepack pnpm test:collaboration
# 启动主服务后
corepack pnpm smoke
corepack pnpm exec playwright install chromium
corepack pnpm test:e2e
# 容器方式启动后
corepack pnpm test:containers
```

集成测试创建随机命名的独立测试数据库，结束时仅清理该测试库；不向本地开发库填业务数据。浏览器测试通过接口替身验证异常、权限撤销及范围切换；`test:collaboration` 使用隔离数据库和仅存在于测试中的协作服务，验证真实生产构建的 HTTP 链路。真实站点兼容性需另外联调。

CI 配置在 `.github/workflows/ci.yml`，覆盖格式、静态检查、PG 集成、构建、MCP/HTTP 冒烟和浏览器用例。远端执行结果以 GitHub 实际运行记录为准。

## 6. 备份与恢复

```bash
corepack pnpm db:backup
corepack pnpm db:restore:check
```

备份保存在被 Git 忽略的 `data/backups/`。恢复检查选择最新备份，创建独立临时库，验证扩展、schema、应用权限及 RLS 后清理，**不会覆盖原库**。生产恢复须同时保留数据库角色/密钥和产物存储；当前脚本演练的是同一 PG 实例内的基础数据库恢复，不宣称已验证跨机器灾备或业务产物一致性。
